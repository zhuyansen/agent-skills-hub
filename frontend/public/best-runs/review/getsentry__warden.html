## 1. [medium] Cancellation overwrites a payment completed after the status check

- Skill: code-review
- Severity: medium
- Confidence: high
- Location: `shop/orders.py:37`

If payment completes between cancellation's status query and update, cancellation overwrites `paid` with `cancelled` despite the successful charge. Enforce the unpaid condition atomically in the cancellation update and handle a failed transition.

Verification:

- The reported `cancel_order()` change rejects a status of `paid`, then updates the order by ID alone; the update does not recheck its status.
- `payments.pay()` calls `Gateway.capture()` and then writes `paid` through `db.execute()`, which commits the change.
- If cancellation reads `new`, payment captures and commits `paid`, and cancellation then executes its update, the captured order ends in `cancelled`, contradicting the explicit rejection of paid orders.
- `shop/db.py` enables cross-thread connection use and provides no lock spanning the status query and update. The inspected checkout contains the base orders implementation; the cancellation statements are supplied by the candidate's change excerpt.

## 2. [medium] Missing ownership check allows cancelling another user's order

- Skill: security-review
- Severity: medium
- Confidence: high
- Location: `shop/orders.py:32-37`

A caller can supply another user's unpaid order ID and cancel it because `cancel_order` ignores `user_id`; enforce ownership before updating the order.

Verification:

- The added `cancel_order(order_id, user_id)` service function accepts a caller-controlled order ID but never uses `user_id`.
- Its lookup checks only existence and whether the status is `paid`; an order belonging to another user with status `new` passes both checks.
- The update selects solely by order ID, and `shop/db.py::execute` executes and commits the SQL without an authorization guard.
- `get_order` explicitly compares the stored owner with `user_id` and raises `Forbidden` on mismatch, but the new cancellation path does not invoke that check.

## 1. [high] Retry loop never advances and hangs on persistent capture failures

- Skill: code-review
- Severity: high
- Confidence: high
- Location: `shop/payments.py:30-35`

`attempt` is never incremented after a failed capture, so a gateway that continues raising `PaymentError` loops forever instead of stopping after `MAX_ATTEMPTS`; the order remains unpaid and `pay` never returns.

Verification:

- `pay()` initializes `attempt = 1` and enters `while attempt <= MAX_ATTEMPTS`.
- The `except PaymentError` branch only logs; it does not change `attempt`, so the loop condition remains true on every failure.
- `Gateway.capture()` raises `PaymentError` while `fail > 0`, and a gateway that persistently raises is a reachable capture failure path.
- The database update and success log occur only after the loop, so persistent failures hang before the order can be marked paid or the error can be surfaced.
