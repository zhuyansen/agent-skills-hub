pr-03-search-by-note
SQL injection: search_orders builds the query with an f-string from user-supplied text instead of parameters.
The review
# roborev review: pr-03-search-by-note

- Tool: roborev (`roborev review --branch=pr-03-search-by-note --base main --wait`), agent opencode, model astra/gpt-6-astra
- Job: 2 (3705ce9..bcaa937)
- Verdict: **Fail**

## Summary

Adds search_orders for a user's orders by note text, but constructs the SQL query through string interpolation.

**Agent assessment:** Fail

## Findings

### 1. High

**Location:** shop/orders.py:33

**Problem:** `search_orders` interpolates both `user_id` and `text` directly into SQL. A note search such as `%' OR 1=1 --` changes the WHERE clause and returns orders belonging to other users; an apostrophe can also produce a SQL error. This is reachable whenever the search text is supplied by a user or other untrusted caller, causing cross-user data exposure.

**Fix:** Use parameterized SQL: `db.query("select id, status, total_cents from orders where user_id = ? and note like ? order by id", (user_id, "%" + text + "%"))`. Escape LIKE metacharacters if the API is intended to search for literal text.

### 2. Medium

**Location:** shop/orders.py:33

**Problem:** The raw search text is inserted into a `LIKE` pattern without escaping `%` and `_`, so searching for either character matches arbitrary note content rather than the requested literal text. For example, searching for `_` returns orders with any one-character note, producing incorrect search results.

**Fix:** Escape `\`, `%`, and `_` in the input and add an `ESCAPE '\\'` clause when literal substring matching is required; continue passing the resulting pattern as a query parameter.

pr-06-cancel-order
Missing authorization: cancel_order takes user_id but never checks that the order belongs to that user, so any user can cancel anyone's order.
The review
# roborev review: pr-06-cancel-order

- Tool: roborev (`roborev review --branch=pr-06-cancel-order --base main --wait`), agent opencode, model astra/gpt-6-astra
- Job: 6 (3705ce9..4a5b490)
- Verdict: **Fail**

## Summary

Adds orders.cancel_order to cancel an unpaid order, but the implementation does not enforce ownership and is vulnerable to a payment/cancellation race.

**Agent assessment:** Fail

## Findings

### 1. High

**Location:** shop/orders.py:33

**Problem:** cancel_order accepts user_id but never uses it when looking up or updating the order. Any authenticated user who can obtain another order's ID can cancel that order, because the update is constrained only by id. This violates the ownership check enforced by get_order and allows unauthorized order state changes.

**Fix:** Look up the order's owner and raise Forbidden when it differs from user_id, or include user_id in the conditional UPDATE (and distinguish a missing order from an unauthorized one).

### 2. High

**Location:** shop/orders.py:38

**Problem:** The paid-status check and the unconditional update are separate operations. If payments.pay captures an order after the status SELECT but before the UPDATE, cancellation overwrites the newly paid status with cancelled, leaving a successfully captured payment attached to a cancelled order. Concurrent cancellation calls can produce the same stale-check outcome.

**Fix:** Make cancellation atomic, for example with `UPDATE orders SET status = 'cancelled' WHERE id = ? AND user_id = ? AND status NOT IN ('paid', 'cancelled')`, then inspect the affected row count and handle not-found, forbidden, and already-paid cases appropriately; ensure payment likewise uses an atomic status transition.
found
pr-07-payment-retry
Retry loop never ends and hides failure: `attempt` is never incremented, so a gateway that keeps failing loops forever (and after three real failures the order would still be marked paid, since nothing re-raises).
The review
# roborev review: pr-07-payment-retry

- Tool: roborev (`roborev review --branch=pr-07-payment-retry --base main --wait`), agent opencode, model astra/gpt-6-astra
- Job: 11 (3705ce9..eae6b1d)
- Verdict: **Fail**

## Summary

The commit adds a retry loop for payment capture, but it does not enforce the intended three-attempt limit.

**Agent assessment:** Fail

## Findings

### 1. Medium

**Location:** shop/payments.py:35

**Problem:** The attempt counter never advances, so every PaymentError repeats attempt 1 indefinitely. With the supplied Gateway and fail = 3, pay makes a fourth capture attempt and marks the order paid instead of stopping after three attempts. A gateway that keeps raising PaymentError leaves the caller stuck in an unbounded loop, repeatedly issuing capture requests and warning logs.

**Fix:** Use a bounded three-attempt loop and re-raise the final PaymentError when attempts are exhausted. Only update the order to paid after a successful capture; simply incrementing the counter would otherwise allow exhausted retries to fall through to that update. Add behavioral tests for recovery within the limit and exhaustion, asserting the capture-call count, propagated error, and unchanged order status on failure.
found
