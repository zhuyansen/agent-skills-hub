This is under 50 lines, so the review covered Steps 1–3, Step 6b (new names were added) and the Step 7 Quick Test Check. Step 6a was skipped because no imports changed.
**Health Score:** 80/100

The retry loop never increments its attempt counter. Any gateway failure that persists makes `pay()` spin forever, and nothing tests the new retry path.

---

## Findings

### 🔴 Critical

**Cognitive Overload — Hand-rolled retry loop never advances `attempt`, and exhausted retries fall through to "paid"**
Location: shop/payments.py:31
Symptom: `pay()` replaces a single `gateway.capture(...)` call with a manual `attempt = 1` / `while attempt <= MAX_ATTEMPTS:` loop (lines 30–36). Nothing in the loop body increments `attempt`. The `except PaymentError:` branch only logs, so `attempt` stays at 1 and a gateway that keeps failing traps the loop forever. The loop also has no failure path after the last attempt. Once someone adds the increment, exhausting all attempts still falls through to `update orders set status = 'paid'` (line 37) without a successful capture, because the last `PaymentError` is swallowed.
Source: Code Complete — Ch. 16 Controlling Loops: use a counted loop when the iteration count is known, and keep loop control in one place. Also Ch. 8 Defensive Programming / error-handling discipline: keep error paths explicit and do not let a swallowed exception hide the failure mode.
Consequence: Today, an outage or a declined card hangs the request or worker thread indefinitely while logging warnings forever. After the obvious one-line "fix", orders will be marked paid without the money being captured. Both are production risks on the payment path, and readers cannot see either failure mode because the loop's control logic is spread across a counter, a `while` condition and a `break`.
Remedy: Replace the manual counter with a bounded loop that has an explicit exhausted path, for example `for attempt in range(1, MAX_ATTEMPTS + 1): try: gateway.capture(...); break; except PaymentError: log.warning(...)` followed by `else: raise PaymentError(...)`. Alternatively, re-raise on the last attempt. Either way, the `status = 'paid'` update must only run after a capture succeeds.

### 🟡 Warning

**Coverage Illusion — New retry behavior has no tests**
Location: tests/test_shop.py:26
Symptom: The diff adds retry-on-`PaymentError` behavior to production code but changes no tests. The only payment test, `test_pay_marks_order_paid`, uses a fresh `Gateway()` with `fail = 0`, so it only runs the first-try success path. `Gateway.fail` exists to simulate failures, but no test sets it to cover "fails once then succeeds" or "fails on every attempt".
Source: Working Effectively with Legacy Code — Ch. 1 (code without tests is legacy code; changes need tests that sense the new behavior)
Consequence: The infinite-loop defect above passes the existing suite. Future changes to the retry count or the exhausted-retries behavior will also go unchecked, so the payment path's error handling stays happy-path only.
Remedy: Add `test_pay_retries_after_transient_failure` (set `gateway.fail = 2`, assert the order is paid and `gateway.captured` has one entry). Also add `test_pay_gives_up_after_max_attempts` (set `gateway.fail = MAX_ATTEMPTS`, assert `PaymentError` is raised and the order status is not `paid`).

---

## Summary

Fix the retry loop before merging. Make it a bounded loop that raises when it runs out of attempts, and only mark the order paid after a successful capture. Add tests for the transient-failure and exhausted-retries paths so the suite actually covers the new behavior. The change is small and in scope (no Change Propagation concerns), and `MAX_ATTEMPTS` is properly named, but right now it makes the payment path worse.

**Health Score:** 80/100

Do not merge this as is. The PR stops checkout from crashing by swallowing every gateway failure and then marking the order paid, which turns a visible error into silent revenue loss.

---

## Findings

### 🔴 Critical

**Domain Model Distortion — Failed card capture is silently swallowed and the order is still marked 'paid'**
Location: shop/payments.py:29
Symptom: `pay()` now wraps `gateway.capture(...)` in `try: ... except Exception: pass` (lines 27–30). After that it unconditionally runs `update orders set status = 'paid'` (line 31) and logs `"order %s paid"` (line 32). When the gateway raises `PaymentError("gateway timeout")`, or any other exception including programming errors like `TypeError`, the error is dropped with no log, no re-raise and no status change. The order is recorded and logged as paid even though no money was captured. `PaymentError`, which the module defines as its failure signal, can no longer reach any caller.
Source: McConnell — Code Complete, Ch. 8 Defensive Programming (error-handling discipline: explicit error paths, never silently discard errors); Evans — Domain-Driven Design, Domain Model pattern (the `paid` status must reflect the domain fact that payment was captured)
Consequence: This creates production risk today. Every gateway timeout or decline becomes an order that is fulfilled without payment. The audit log says "paid", so the failure is invisible to operators and to maintainers. Callers can no longer tell success from failure, so retry, alerting and customer messaging can't be built on top of `pay()`. The bare `except Exception` also hides real bugs in the capture path.
Remedy: Remove the blanket `except Exception: pass`. If checkout must not crash, catch only `PaymentError`, log it with the order id (`log.warning`/`log.exception`), and record a distinct state (for example `status = 'payment_failed'`) or re-raise a domain error for the checkout layer to turn into a user-facing message. Only run the `status = 'paid'` update and the "paid" log line after `capture` returns successfully, for example in a `try/except PaymentError/else` structure.

### 🟡 Warning

**Coverage Illusion — Changed gateway-failure behavior of pay() has no test**
Location: shop/payments.py:27
Symptom: The diff changes the production behavior of `pay()` when `capture` raises, but includes no test changes. `tests/test_shop.py` has only `test_pay_marks_order_paid` (happy path, line 26). Nothing exercises `Gateway.fail > 0`, even though the `Gateway` stand-in exists specifically to simulate that failure.
Source: Feathers — Working Effectively with Legacy Code, Ch. 1 (code without tests is legacy code; changes need a sensing test)
Consequence: The suite stays green while failed captures mark orders paid. A test asserting the status after a gateway failure would have exposed the Critical finding right away. Whatever failure behavior is chosen next can regress the same way without anyone noticing.
Remedy: Add a test such as `test_pay_gateway_failure_does_not_mark_order_paid`. Set `gw = payments.Gateway(); gw.fail = 1`, call `pay`, and assert either that the expected `PaymentError` or domain error is raised or that the order status is not `'paid'` (for example `'payment_failed'`). Also assert that `gw.captured` is empty.

---

## Summary

The most important fix is to stop swallowing capture exceptions and only set `status = 'paid'` after a successful capture. Handle `PaymentError` explicitly with logging and a failed-payment state. The PR is small and touches only one module, so change propagation is fine, but it trades a loud failure for a silent one. A failure-path test should come with the fix so the payment contract stays protected.
